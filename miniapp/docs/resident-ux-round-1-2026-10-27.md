# 桂平居民养老体验反馈 · 第1轮

日期：2026-10-27。基线：2.22.1 / fe4f1f3。状态：**本轮完成体验与反馈；产品修复尚未开始，下一轮先读本文件。**

## 本轮实际做了什么

以广西贵港（桂平户籍）为背景，运行19组页面事件流程：选地区 → 填年龄或出生年月 → 选历史档或手填 → 算普通结果 → 开补缴 → 选1000元年档对应的月领结果 → 改一年的目标 → 不勾资格直接尝试应用 → 取消。另含查记录、从未参保、已领取与账户余额路线。脚本没有执行真正缴费、经办确认或外部查询。

执行的是小程序真实JS事件方法及原计算器，Node VM模拟Page/setData/wx，结合WXML读文案和入口顺序。**没有打开微信开发者工具、没有渲染手机屏幕、没有真人访谈。** 下文第一人称为角色推演，不是假称农村老人真实说过这些话；键盘、滚动、点击热区、字号、屏幕阅读器及设备性能仍未验证。

固定数据截至2026-10，便于下轮对比，不让日期漂移影响结果。只填周岁时月份由当前模型推定，表中时间与金额是程序输出，不是新政策核定、不是保证领款日期。桂平按现有贵港入口，不新增一个刻意的县级选择。

19例均执行完成，18例普通结果可算；已领取者1例被拦截。16例进入快捷补缴，其中14例能预计算，2例因历史平均数／月缴记录中断。16例尝试应用时均未擅自勾确认、未改原数据；取消亦保留原数据。没有把“没抛异常”当作体验合格。

## 普通用户角色反馈与问题清单

### UX-01 / P1 / 待修复：先给很晚的年龄，用户容易认为是定论

证据：G03先显示69岁，G04显示71岁，G07显示75岁；同一份信息进补缴预览才显示另一条参考路线。不是本轮认定这些算术错误，而是主结果的顺序和解释让普通用户先受惊、再去找入口。

角色推演：“我已经60岁了，怎么还要等到71？如果不知道点补缴方案，我就关掉了。”

下一轮最小修复：主结果将当前路线明确写成“只按以后每年交”，在接下来缴费卡紧接一个清楚的补缴比较入口；对已到龄／接近到龄优先让人知道还有附条件的补缴参考。不得强行把领取年龄改为60、不得把费用参考当批准。

验收：G03/G04/G07一眼能区分当前年缴路线和可比较补缴路线，不增加大段政策卡；原逐年费用、资格阻断、取消恢复不变。

### UX-02 / P1 / 待修复：最需要帮助的“记不清”用户，反而不能选方案

证据：G09可以得到约220元的普通结果，点击补缴后进入“先把记录查清楚”，只能去村委／窗口问三类问题后再回来。G08从未参保进入逐年手填，不能得到同等层级的简单下一步。

角色推演：“我就是不知道，才来算。又让我去查，我还是不知道大概要准备多少钱。”

下一轮最小修复：记不清时可保留附条件的费用范围／“先看大概”，与已核明细严格分开；实填或参保登记仍用于正式方案。先修G09，不为G08虚构老参保资格。查记录作为后续核实，不变成所有参考比较的前置门槛。

验收：G09至少能比较几种清楚标假设的费用和月领参考，不生成虚构已确认年度、不给假资格自动打勾；G08明示先登记核可补条件而非让人盲填历史。

### UX-03 / P1 / 待修复：允许填平均数／月缴，但补缴页报错没有解释和退路

证据：G12年缴平均333元、G17每月16.67元，都能算普通结果；补缴页六个卡片为空，只报“请核对已交年份及原缴费档次”。这不是用户输入错，而是两种页面对数据精细度要求不同。

角色推演：“前面不是让我自己填吗？怎么现在又说不对？我要改成多少才对？”

下一轮最小修复：解释“平均金额可算账户大概，过去提档需要各年实际档”；仍可看以后换档、不改过去的费用比较，另给查询／分年输入入口。严禁把333改成300、把月缴乘12后凑成合法档，或假装这些是真实年度记录。

验收：G12/G17没有空白死路，给出能继续的操作；普通结果与原金额不被修改。历史提档引擎仍拒绝不合法原档。

### UX-04 / P1 / 待修复：默认最高档且把参考方案“应用”绑在经办核实上

证据：G03一进就选中约660元、总64000元；G04默认约620元、总59200元。用户尚未表达预算。16例点击“用这份方案”都需要先确认原记录／可补范围／补贴；推定年份与已查询年份走相同的应用按钮。

角色推演：“我只是看看，不是要交六万。你配的年份我也不知道对不对，这个勾我敢不敢点？”

最小方向：入页延续原年档或先不选；明确“参考对比”与“核对后加入”的区别，提供保留假设的比较状态，不能为了方便把gxScopeReviewed改为yes。高额支出不默认成为用户意愿。

验收：G03/G04默认选择能解释，假设仍显眼，未经核对绝不写入已确认补缴记录。

### UX-05 / P2 / 待修复：已交满和年轻人仍见“补到15年”的相同页头

证据：G06已满15年、还需缴0元，却仍显示“到60岁交够15年／现在补够15年”；G01/G14不需要补漏年，快捷方案主要是提高过去档次和以后缴费，名称仍以补足为中心。

角色推演：“我不是交够了吗？这里到底是在补没交的，还是再给一遍？”

最小方向：按缺年情况只展示有意义的模式；已满15年突出无需再补年数，是否提高月领另选，不默认推荐花57000元提档。

验收：G06能看到“年数已够”；G01/G14不会把补漏0年包装成必须补缴。

### UX-06 / P2 / 待修复：今年没交时，本年款被写进“以后每年交”

证据：G15今年未交，预览现在补52000元，“以后每年交6000 × 2年，2026—2027”。普通用户容易以为今年只交52000，不知道2026年正常缴费6000也在待交范围。G16未知本年状态暂按已含，虽然有文字提示，费用时点依然容易漏读。

角色推演：“现在要准备52000还是58000？你写以后的，是明年才交吗？”

最小方向：拆成本年正常缴费／历史补缴／以后年缴，主卡仍只回答现在要准备、以后每年、何时领；不改变总额64000和缴费年份。

验收：G15本年6000不会隐在“以后”；G16清楚表明本年状态是假设。没有重新发明统一缴费截止日。

### UX-07 / P2 / 待修复：普通结果、补缴页、换个方案有三套不同的调整范围

证据：普通页“换个方案”只改未来；补缴页单年修改也会改变过去的拟提档；完整年度编辑又是逐段手填。含义靠说明文字区分。G11输入四段历史需12次字段事件，叠加初始填写和比较共32次事件调用（不是手机点击数）。G10连续段和漏年必须先学会拆段。

角色推演：“我只是想多领一些，不知道应该改上面还是下面，改了会不会把以前的钱改没了？”

最小方向：固定显示“过去已交不变”，把以后换档和补漏／补差放到一个方案的清楚分组；默认比较不要求逐年编辑，详细输入只在用户确实有记录时展开。

验收：G11原本金30200元不变，已有6000档不重复收费；修改／取消／切省各自有一致边界。

## 外部信息负担

- 能先得到普通结果：年龄、年数、历史金额、地区即可；不需要先查账户余额。G19查到余额时也能使用，并且不会重复加入原本金。
- 只想看费用预览：14例无需查询就能得到方案，但其中多例使用明确推定年份，不能把“有数”理解成已具资格。
- 想真正加入历史补缴：需要实际年份、原档、可补范围及必要补贴核实；这些是现实办理所需信息。问题是产品没有把“先作选择”和“交钱前核实”分清，不能靠自动勾确认解决。
- G09被直接送去窗口，G12/G17需要另外找实际年度档次且页面没有解释。这是本轮最明确的额外负担。
- 脚本没有外部查询，不表示真人现实使用时外部查询为0次；也没有测试电话、政策链接打开或窗口办理情况。

## 这版值得保留的部分

档次下拉和自填都有入口；完整分年记录能识别真实断缴；混合高档历史不被重复收费；修改目标后月领会重算；预览取消后原数据恢复；未经确认无法自动应用；已领取者明确被拦截。不要为减少文字拆掉这些约束。
